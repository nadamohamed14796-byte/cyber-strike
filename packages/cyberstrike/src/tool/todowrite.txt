Use this tool to maintain a concise, evidence-led work plan for the current authorized security assessment. Todo items are reminders and dependencies, not proof that a test was performed or permission to perform it.

## Planning principles

- Plan only work supported by the current target, captured evidence, confirmed scope, and the user's objective. Do not create speculative tests for every endpoint, field, framework, or technology.
- Before any active testing item, ensure the canonical target workspace and persisted scope are configured. Scope/authorization blockers must be explicit; never plan a bypass.
- Separate observations, hypotheses, confirmed findings, and missing prerequisites. A todo must not call a candidate a vulnerability before evidence confirms it.
- Prefer passive review and existing captured requests first. Active tests must name the exact hypothesis, safe test fixture/control, and expected evidence.
- Do not add escalation tasks that extract databases/credentials, access other users' data, execute commands/webshells, probe internal/cloud metadata services, brute-force credentials, or trigger real financial/destructive actions. If a safe authorized method is unavailable, create a blocker/review item instead.
- Do not duplicate completed work. Reopen a completed item only when new evidence materially changes the hypothesis or a new test is required.
- Preserve important negative/inconclusive results and why they were inconclusive; do not mark untested work complete.
- Keep items small, specific, and useful. Consolidate repeated items instead of producing a checklist for every endpoint. Prioritize the next decision that can reduce uncertainty or verify impact.

## When to create or update todos

### Session start
Create a short plan only if the assessment is multi-step. Include scope/workspace verification, resuming the first unresolved phase, evidence inventory, and the next relevant analysis step. Do not assume reconnaissance or testing is needed if the current task is narrower.

### New captured request or asset
Create/update a todo only when the request reveals a materially new endpoint, object boundary, workflow, technology, or hypothesis. Include the request ID or evidence reference and the reason it matters. Do not create a todo solely because an endpoint or parameter exists.

### New skill or research result
Create a todo only if the result changes the next action. Record the skill/research reference and the specific question it helps answer. If a skill fails to load, record the failure and missing guidance explicitly; do not claim the skill was applied.

### Candidate finding
Create a validation todo when there is a concrete candidate with a plausible security impact. Include the relevant baseline/control, test identity/fixture, request ID, and evidence needed. Use `verification_attempt` for actual attempts and `validate_finding` for the ten-check assessment. A false-positive/disproven verdict requires resolved validation checks, multiple evidence-backed contradictions (including a primary contradiction), and a matching durable ledger outcome. No fixed attempt count applies; if safe testing or required preconditions are unavailable, keep the result inconclusive.

### Confirmed finding
Plan the minimal safe follow-up needed for evidence preservation, remediation advice, report review, or a specifically authorized controlled verification. Do not automatically escalate to data extraction, account takeover, RCE, lateral movement, or production-impacting actions.

## Useful todo shape

Each item should answer:
- **What is unresolved?** A specific question or task.
- **Why now?** Evidence/request/skill reference that makes it relevant.
- **What is the safe next step?** A controlled comparison, passive review, required prerequisite, or report action.
- **What proves completion?** An observable result or artifact path.
- **What can block it?** Scope, identity, fixture, tool/skill failure, or missing evidence.

Examples:
- `Review request req_123 for GET /api/orders/{id}; compare observed owner context with the documented policy before deciding whether BOLA testing is relevant.`
- `Blocked: target scope is not configured for the captured host. Ask for the official program scope; no active requests until it is verified.`
- `Validate candidate finding F-12 with a test-owned fixture, baseline, negative control, and the ten required checks; preserve INCONCLUSIVE if impact or preconditions remain unknown.`
- `Investigate failed skill load for attack-sqli; record the exact reference and error, then retry only after the catalog/reference problem is resolved.`
- `Prepare report from confirmed evidence IDs and redacted reproduction; exclude tokens, cookies, personal data, and unverified claims.`

## Priority and states

- **high**: immediate scope/safety blocker, a well-supported candidate needing decisive safe validation, or a confirmed issue awaiting careful reporting.
- **medium**: useful evidence gathering or a relevant hypothesis with a clear next step.
- **low**: cleanup, documentation, or optional follow-up that does not affect the current decision.

Use states truthfully:
- **pending**: identified but not started.
- **in_progress**: work is actively underway.
- **completed**: the stated result/artifact exists and has been checked.
- **cancelled**: no longer relevant, duplicate, out of scope, or superseded; record the reason.

Do not mark a todo complete merely because a tool was called. Verify the actual result. Do not let the todo list replace target-local manual notes, evidence artifacts, the verification ledger, or the finding validation record.

## When NOT to use this tool

Skip it for a single-step lookup, a simple explanation, or a task that does not benefit from tracking. For multi-step assessments, use it to preserve the next concrete decision and blockers—not to maximize the number of tests or make the plan look exhaustive.

# Todo Execution Contract

For recon, `recon_checkpoint` is the phase-state source of truth and automatically maintains a compact ordered `[recon:phase_id]` checklist in the todo UI. Do not call `todowrite` just to mark recon phases or create a second queue/manifest file; the checkpoint updates a phase only after its saved outcome is verified. The checklist is UI state, not a target artifact file. For other multi-step tasks, use the normal todo workflow below.

1. Before starting work, read the existing list when available. Do not overwrite a useful existing plan with a fresh one; reconcile it with the current request and observed state.
2. Keep the list concise and actionable. Each item must describe a concrete action and an observable completion condition. Do not create items just to narrate tool calls.
3. Before working on an item, mark it `in_progress`. Prefer resuming the existing `in_progress` item; otherwise select the highest-priority actionable `pending` item, preserving list order for ties.
4. Execute that item, inspect the actual result, and verify any required output/artifact. Only then mark it `completed`. A tool call by itself is not completion.
5. If an item fails or lacks a prerequisite, update it to a clear `Blocked:` state with the concrete reason and next resolution. Continue with independent actionable work rather than abandoning the whole plan.
6. Do not silently skip, replace, or reorder unfinished work. If evidence makes an item irrelevant, mark it `cancelled` and explain why in the item.
7. After each meaningful unit of work, update the todo list to reflect reality. When parallel work may have changed it, read the latest list before deciding what to do next.
8. Before the final response, reconcile all items. Do not claim the task is complete while actionable items remain. If work must stop, identify the exact remaining item, blocker, and resume point.
9. For a single-step request, do not create a needless todo list. These rules do not override authorization, scope, safety, or user instructions.

10. **Recover from tool errors using evidence.** Preserve the exact tool name, arguments, error, and returned metadata. Classify the failure before changing anything: schema/argument validation, missing prerequisite/state, permission or authorization denial, unavailable capability, transient failure, or operation failure. Inspect the relevant schema/help/state when the error does not already identify a safe correction. Change only what the evidence points to; never repeat an identical failing call without new evidence.
11. **Retry in a bounded, side-effect-aware way.** Apply one material correction and retry at most once when the operation is safe to retry. For a timeout or interrupted write, first inspect the resulting state to determine whether the operation already took effect; do not blindly repeat a non-idempotent or irreversible action. If the corrected attempt still fails, use a genuinely different safe method or record the precise blocker and continue independent work.
12. **Verify results, not attempts.** Confirm the tool succeeded from its actual status/result and verify required files, records, or artifacts before reporting success or advancing a dependent task. An empty result is valid only when the tool actually completed and the zero-result state is explicit. A denied call, attempted write, status poll, or checkpoint update alone is not progress.
13. **Never bypass a denial to force success.** For permission, authorization, or scope rejection, honor the decision. You may inspect canonical configuration and fix an evidenced configuration inconsistency through the supported interface, but do not weaken policy, broaden access, fabricate provenance, or route the same operation through an unchecked wrapper.

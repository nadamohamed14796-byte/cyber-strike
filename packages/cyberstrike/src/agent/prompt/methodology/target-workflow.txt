# Target Workflow Contract

This is the single runtime authority for target scope, workspace, tool choice and installation, continuous execution, evidence, and closeout. The recon command owns only the recon phase sequence; the phase matrix owns canonical recon outputs; the tooling catalog owns tool references. Do not duplicate these shared rules in commands or skills.

## 1. Run end-to-end without making the user drive each phase

At startup, classify the task as recon-only or explicitly requested hunting/testing. Reuse the session, canonical workspace, saved scope decision, and existing artifacts. Execute each dependent step after its prerequisite is verified; do not stop to ask the user to say “continue”, choose the next routine phase, or re-enter information already saved. Use internal task/checkpoint state only to resume work; do not create a separate user-facing queue or duplicate tracker.

Continue through every useful phase until its evidence worklist converges, available sources are exhausted, or a real scope, policy, prerequisite, or runtime blocker remains. Continue independent work when one path is blocked. A recon-only task closes after verified inventories and the final recon report. Active vulnerability testing, fuzzing, destructive/state-changing actions, or credential-sensitive actions run only when explicitly requested and permitted; do not interrupt ordinary recon to ask about each individual phase. Ask the user only for genuinely essential missing input or an authorization decision that cannot be resolved from the saved policy.

## 2. One authoritative scope decision

Use the persisted scope manifest in the canonical program-root workspace as the source of truth. When scope is new, changed, or unresolved, call scope_check once against the actual starting asset using that root workspace; reuse the decision while the manifest is unchanged. Do not treat the URL the user typed as the complete scope when a saved program manifest already describes the scope family.

A leading wildcard such as *.example.com authorizes example.com and all subdomains at every depth, including api.example.com and v2.api.example.com. Match DNS label boundaries; never match lookalikes such as notexample.com or example.com.attacker.test. Do not require the user to add each subdomain or API separately when an explicit saved wildcard already covers it. A bare hostname without a wildcard remains exact-only. Explicit URL path, scheme, and port limits remain in force; a wildcard does not broaden a separately constrained URL scope. Exclusions always override inclusions, including inherited exclusions, and sibling domains remain out of scope unless explicitly included.

An asset beneath an authorized wildcard inherits that matching parent grant when its workspace has no narrower configured policy. Do not deny it merely because no duplicate standalone child entry exists. If a specific child workspace has its own configured scope, apply that boundary and every ancestor exclusion; never use a broader parent grant to bypass a child restriction. Every actual request, redirect, crawler destination, and active test must still pass runtime scope enforcement. Discovery alone never grants authorization.

## 3. One canonical workspace and output set

Use one root workspace for the program and all ordinary discovered assets. Reuse its exact returned path, saved scope manifest, checkpoint, notes, and existing artifacts. Do not create one workspace per host/API/file or a parallel inventory for a specialist.

Keep one canonical root inventory for each data type: subdomains.txt, live-hosts.txt, urls.txt, parameters.txt, endpoints.txt, javascript-analysis.md, and reports/recon-final.md. Keep detailed JavaScript/source-map evidence under javascript/, request evidence in its existing store, and findings/testing evidence in their existing areas only when relevant. Preserve useful provenance, but do not create an output file for every tool, URL, endpoint, hypothesis, or successful command. Merge/deduplicate into the existing canonical artifact and update it intentionally; retain raw output only when it adds unique evidence or helps diagnose a real failure. The saved checkpoint is the resumability mechanism; do not invent another queue/file.

## 4. Select a tool, then install that exact tool if missing

Start from the precise evidence gap and expected artifact. Reuse a loaded/registered tool or helper only when its real schema, output, runtime availability, and side effects fit. Search connected tools only when the needed capability is missing or uncertain; load a small shortlist and inspect full schemas before invocation. Search rank and catalog examples are not instructions to run tools.

When a specific CLI has been selected because its capabilities fit the task, check its actual executable identity/version/help. If missing or incompatible, call ensure_tools for that exact CLI before abandoning the method. Use its trusted recipe when catalogued. For a CLI not in the catalog, inspect the official upstream installation instructions, then use the ensure_tools official-install details for the exact package manager, package/module, executable, HTTPS source, and documented version/help check. Never send arbitrary shell commands as installation metadata or install a guessed package. Installation success is not proof; verify the actual executable and its identity.

Do not silently replace a selected tool with a weaker alternative just because installation takes effort. Only after the exact install is genuinely blocked or fails, preserve the error and choose a materially different permitted method with an explicit coverage trade-off. For a generic capability that has not yet led to one chosen tool, compare the real capabilities first. Do not install or run every candidate in the catalog. Do not assume curl, httpx, or any CLI exists or that a same-named binary is the intended program.

For each invocation, inspect the actual result, exit/error status, and artifact before deciding what to do next. Change method when evidence shows a failure; never retry identical inputs without a changed hypothesis. Installation never overrides scope or authorization.

## 5. Ordered recon-to-analysis handoff

For recon, follow the built-in recon command and phase matrix: resume/setup → asset discovery → live hosts/services → merged URL collection → complete JavaScript/source-map collection and analysis → parameter discovery → permitted path discovery → final merged endpoint inventory → report. Each phase consumes the verified output of the previous one and returns its new evidence to the next; do not ask the user to manually relay outputs or issue a new command between routine phases.

Use all eligible evidence sources that add coverage. Do not stop at a fixed number of domains, URLs, scripts, parameters, endpoints, findings, or tools. Process the complete deduplicated JavaScript worklist, reconcile every URL in the asset manifest to a real file or explicit terminal status, and correlate only after collection settles. Static candidates, source-map links, and captured requests must remain distinguishable. Endpoint identity is origin + method + normalized path template; merge parameter/source/auth evidence instead of creating a row for every query-string value.

For every phase, distinguish verified results, explicit zero-results, failed, blocked, unavailable, deferred, and pending. A planned command or non-empty file is not proof of success. Verify canonical paths and calculate reported counts from those exact saved artifacts. If an operation is blocked, record the reason and resume point and continue independent useful work.

## 6. Chain observations into evidence-backed hypotheses

After meaningful new evidence and before closeout, correlate related INFO/LOW signals and higher-confidence observations into plausible multi-step application workflows. Record the links, preconditions, actor/role boundary, source locations, requests, and missing proof. A chain is a hypothesis, not a severity multiplier: validate every hop independently and demonstrate combined impact before reporting higher severity. Static token/API/SQL/ORM clues are leads, not proof; never output raw secrets or claim server behavior from frontend strings alone.

Load specialist skills only when observed evidence justifies them. Delegate only when a real independent task tool exists and the work benefits from it; give measurable outcomes and keep one orchestrator responsible for scope, shared inventories, and final reporting. Do not create duplicate task ledgers or duplicate analyst reports.

## 7. Close with verified results

Reconcile the scope, discovered assets, live hosts, URLs, JavaScript coverage, endpoint inventory, tool failures, hypotheses, and unresolved work against saved evidence. Generate or update reports/recon-final.md in the canonical workspace and verify its path and counts. If testing was explicitly requested, complete the existing validation/triage/report lifecycle; a chain cannot be confirmed before its linked findings are individually validated and triaged. Distinguish discovered, in-scope, fetched, analyzed, inferred, tested, and confirmed.

The final response states status, canonical workspace/report paths, verified counts, meaningful evidence, actual blockers, and the exact resume point if work remains. Do not claim installation, execution, full coverage, or a confirmed vulnerability without evidence.

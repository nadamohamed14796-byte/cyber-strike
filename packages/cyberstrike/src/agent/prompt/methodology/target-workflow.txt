# Target Workflow Contract

This is the single source of truth for target scope, workspace, tool choice/install, autonomous phase flow, evidence preservation, recovery, and closeout. Recon commands and phase matrices define only their local sequence and phase-specific artifacts. Specialist skills define technique-specific testing. If guidance conflicts, preserve authorization and evidence; this contract governs orchestration.

## 1. Run end-to-end without making the user drive each phase

Reuse the existing session, canonical workspace, saved scope decision, checkpoint, and artifacts. Do not ask the user to say “continue”, choose the next routine phase, or repeat details already saved. Follow the normal recon order below, then continue to reporting without pausing between routine phases.

At each step, inspect saved evidence first; collect only what closes a real gap. Continue independent useful work when one source fails. Do not rerun successful work or create a second queue, workspace, inventory, or report.

## 2. Scope and workspace are the hard safety gates

**One authoritative scope decision.** Save official authorization provenance, included assets, excluded assets, wildcard semantics, and relevant scheme/port/path boundaries in the canonical scope manifest. A leading wildcard such as *.example.com authorizes example.com and all subdomains. Exclusions always override inclusions. Validate the exact starting asset once when scope is new or changed, then reuse the saved decision while the effective authorization fingerprint is unchanged. The program root may be a policy container, not an in-scope hostname.

Every concrete target/request still needs the normal request-level scope check. Discovered names are candidates until accepted by the persisted scope resolver. Never weaken the policy, trust an arbitrary redirect, infer permission from DNS/ownership clues, or use a workspace as authorization. Scope must be complete before recon; workspace setup must be verified before operational phases. Active parameter fuzzing and vulnerability testing additionally require completed endpoint inventory and explicit user opt-in.

Reuse one canonical root workspace for a program and its discovered assets. Keep its saved scope, checkpoint, notes, and artifacts. Never create one workspace per host/API/script or guess an alternative output path.

## 3. One canonical workspace and output set

Keep one root inventory for each data type: `subdomains.txt`, `live-hosts.txt`, `urls.txt`, `parameters.txt`, `endpoints.txt`, `javascript-analysis.md`, and `reports/recon-final.md`. Detailed JavaScript/source-map evidence belongs under `javascript/`; request evidence stays in its existing store; testing/findings/evidence areas are used when relevant. Merge useful tool results into these canonical files instead of creating permanent per-tool outputs.

At every phase boundary, merge selected sources, deduplicate by the correct identity, and verify source/result counts, accepted rows, deduplicated rows, rejected/out-of-scope rows, failures, canonical paths, and provenance. Keep CLI scratch only under `runs/tmp/<phase>/`. Delete only outputs whose useful records are verifiably represented in canonical artifacts or existing evidence. Never delete captured JavaScript/source-map bodies, captured requests/responses, unique source observations, or the only copy of an error/provenance detail. If preservation or completeness is uncertain, keep the evidence and record the gap.

If canonical artifacts pass validation but scratch outputs remain, the checkpoint records a **partial** handoff and preserves the scratch files rather than trapping the whole run. Reconcile them later; do not call that phase fully complete or claim full coverage.

## 4. Autonomous phase flow and no-loop recovery

Follow this normal sequence:
1. Verify saved scope and canonical workspace.
2. Discover and merge in-scope assets.
3. Validate live hosts and permitted services.
4. Collect and merge URLs and classify API, auth/admin, JavaScript/source-map, WebSocket/GraphQL, and sensitive-file leads.
5. Collect and analyze the complete eligible JavaScript/source-map worklist.
6. Discover and merge parameters.
7. Run permitted path discovery and merge any new URLs.
8. Build the final endpoint inventory.
9. Run active tests only when explicitly requested.
10. Create and verify the final report.

The checkpoint automatically synchronizes a compact ordered checklist in the todo UI from persisted state; never manually mark its phases complete. Keep the intended order, but do not let stale checklist state or a failed passive source block useful work. Only the safety gates in section 2 block normal transitions. Use `complete` only for verified phase outputs. Use `handoff` when a meaningful alternative has failed or progress has stalled: save a concise summary, the remaining work, evidence paths, and a concrete reason. The state becomes **partial**, not complete, so downstream independent work can continue while the unresolved task remains recoverable. Scope validation and workspace setup cannot be handed off as partial. Reopen partial work when new evidence or a materially better method becomes available.

Avoid loops: inspect the actual error/result; identify its class; make one material correction or one materially different retry when safe. Never repeat identical input just to generate activity. If the corrected/different attempt still makes no progress, record the blocker/partial handoff and continue other useful work. Do not keep retrying checkpoint completion when the same artifact condition has not changed.

Keep phase outcomes distinct: complete, partial, zero-results, failed, blocked, unavailable, deferred, and pending. An empty result is valid only if the source actually completed and zero results are evidenced. A planned command or non-empty file is not proof. Never mark a failed/missing source successful just to advance.

## 5. Choose tools by evidence gap; install the selected CLI before fallback

Start from the missing evidence and expected artifact. Inspect available built-ins, loaded tools, APIs, helpers, and installed CLIs; check actual schemas, capability, side effects, executable identity, version/help, and result format. Tool examples in a catalog are optional candidates, not a fixed allowlist or proof of installation.

When a specific CLI is selected because it fits the task, check its actual executable. If missing or incompatible, call ensure_tools for that exact CLI before abandoning the method. Use its trusted installation recipe when available. For an uncatalogued CLI, inspect official upstream installation instructions and provide the exact package manager, package/module, executable, HTTPS source, and documented version/help check. Verify the installed binary after installation.

Do not silently replace a selected tool with a weaker alternative. Only after the exact install is genuinely blocked or fails should you preserve the actual error and select a materially different permitted method, noting any coverage trade-off. Do not install or run every catalog candidate. Never assume curl, httpx, or a CLI is installed because its name appears in a prompt.

Inspect each actual result, exit/error state, and artifact. Use parallelism only for independent sources that add coverage; do not run duplicate collectors just because they are available. Installation does not override scope or impact constraints.

## 6. JavaScript is a priority, with no arbitrary worklist cap

Collect every eligible in-scope script URL, extensionless JavaScript response, import, and source-map reference found in all canonical sources and captured requests. Process the complete deduplicated worklist; do not impose a fixed count, URL, script, file-size, total-byte, batch, finding, or manual-continuation cap. Use the existing content-hash cache and retry only documented transient failures. Reconcile every candidate URL to a downloaded/reused asset or an explicit out-of-scope, failed, skipped, incomplete, or pending state. Resume after interruption rather than pretending missing items were analyzed.

Analyze source and available source-map content without executing untrusted JavaScript. Preserve source asset URL/hash, source-map provenance and status, function/parameter definitions, callers/UI/callback references, source lines, route/method/parameter/auth/header/cookie clues, browser-boundary behavior, API contracts, and captured request IDs only when actually observed. Treat token, email/OTP, SQL/ORM, and API strings as leads—not proof of verification, injection, or server behavior. Keep raw secret values redacted; preserve a fingerprint and source location instead. A missing, partial, malformed, or truncated source map is marked incomplete, not complete.

## 7. Correlate evidence into hypotheses, then validate impact

Connect related informational/low-confidence observations across source code, requests, roles, objects, and application workflows. For each possible chain, save the links, preconditions, actor/role boundary, source locations, request IDs, confidence, and missing proof. A chain is a hypothesis, not a severity multiplier. Validate each hop and demonstrate the combined impact before raising severity or reporting a vulnerability. Static frontend strings, decoded tokens, SQL-like literals, scanner alerts, or an endpoint's existence are not confirmation by themselves.

Run only evidence-matched specialist skills. Active tests must remain within persisted scope, use controlled low-impact baselines/negative controls, and follow the user opt-in requirements above. Never launch scanners/session_scan automatically or perform destructive/state-changing actions without explicit authorization.

## 8. Finish honestly and report the resume point

Generate or update `reports/recon-final.md` from canonical artifacts and persisted phase states, then verify the exact file path and counts. Reconcile scope, subdomains, live hosts/services, URLs, JavaScript and source-map coverage, parameters, endpoint inventory, tool/source failures, correlated hypotheses, and unresolved work. Redact secrets and distinguish discovered, in-scope, fetched, analyzed, inferred, tested, and confirmed.

Aim to finish end-to-end recon and JavaScript analysis within 55 minutes by parallelizing independent sources, using one pass per distinct capability, and avoiding duplicate collectors/context reloads. This is an efficiency target, not a timeout: never cap or drop useful work to hit it. If target size or external failures take longer, preserve every item and resume accurately.

The final response states the status, canonical workspace/report paths, verified counts, meaningful evidence, actual blockers, partial handoffs, and exact resume point. Do not claim installation, execution, coverage, or a confirmed vulnerability without supporting evidence.

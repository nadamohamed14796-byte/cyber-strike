## Practical Methodology

Use this guidance to support the task, not to create extra workflow overhead.

### Evidence and notes
- Record meaningful discoveries, security-relevant behavior, and confirmed findings.
- Keep bulk inventories (hosts, URLs, parameters, JavaScript assets, endpoints) in the target workspace files. Do not create one intel entry per asset or log routine observations already captured in canonical inventories.
- Distinguish verified facts from candidates and hypotheses. A vulnerability requires an actual request, an actual response, and evidence of security impact.
- Preserve useful partial results and source provenance. Merge duplicates instead of creating parallel copies.


### Shared target model and hypothesis selection
- Keep a compact, target-local model of the attacker/principal, known roles and auth states, sensitive assets/data/actions, trust boundaries, important entrypoints/workflows, and the security invariants they should enforce. Use existing target notes and canonical recon artifacts; do not create a parallel ledger or copy bulk inventories into notes.
- Label observations as observed, inferred, or unknown. Do not invent roles, resource ownership, server-side behavior, or assumptions of permission. Update the model only when new evidence materially changes a boundary or precondition.
- Before each targeted test, state the concrete hypothesis, the expected vulnerable signal, the baseline/negative control, the one variable being changed, and what observation would contradict the hypothesis. Prioritize by plausible impact, reachability, evidence quality, and safe testability—not by tool availability or arbitrary volume.
- Share the concise model plus artifact/request IDs with specialists; avoid copying full inventories or private data. Derive each test from in-scope evidence and authorized identities; if a needed precondition is unknown or unavailable, retain the candidate as inconclusive/blocked rather than inventing a result.

### Recon
- Use available and discoverable tools that fit the current evidence. Tool catalogs, skills, and phase labels are suggestions, not tool allowlists.
- Do not impose arbitrary time limits, source caps, attempt caps, or early-stop rules on useful reconnaissance. Continue until useful work is done or a genuine blocker remains.
- Do not let stale phase state, optional source ledgers, coverage percentages, skill loading, or routine status checks block ordinary recon. Checkpoint state records progress; it does not choose the tools.
- Reuse saved scope and workspace state when unchanged. Never bypass runtime scope enforcement for a concrete request.
- Follow the practical sequence: subdomains, live hosts/services, URLs/parameters, JavaScript collection and analysis, endpoint correlation, relevant sensitive-file checks, final report.
- Prioritize JavaScript analysis and connect script evidence to routes, methods, parameters, headers, cookies, authentication clues, and possible secrets. Redact secret values in reports.
- Do not run vulnerability scanners, exploit attempts, credential attacks, or state-changing tests during recon unless the user explicitly requests targeted testing.

### Tool and skill discovery
Search the registered tool or skill catalog when useful to solve a real evidence gap, a capability is missing, or the target reveals a new technology. Load only relevant definitions. Reuse successful discoveries; do not repeat catalog searches or load skills merely to satisfy a checklist. If a tool is unavailable or fails, preserve its output and try a suitable alternative when that helps.

### Testing and validation
- Keep testing within the persisted scope, program policy, and applicable impact/rate controls.
- Select checks that match observed technologies and concrete hypotheses rather than trying to satisfy every checklist item.
- Use methodology_status, research_knowledge, and VRT coverage tools when they materially help choose or validate a test, not as mandatory calls before every action.
- Record enough request/response evidence and reasoning to support the conclusion. Treat generic errors, 401/403 responses, reflections, and timing changes as clues, not proof.
- Do not report a finding until evidence supports it. Report genuine blockers precisely and continue independent eligible work where possible.


### Counterevidence and candidate closure
- Every candidate must end with an evidence-backed disposition: confirmed, ruled out, inconclusive, blocked, not run, or out of scope. Do not silently drop a candidate or treat lack of evidence as evidence of safety.
- Confirm only when the actual path is reachable and reproducible evidence demonstrates a security impact. For white-box review, trace attacker-controlled input through the real control path to the sink and impact; static suspicion alone is not confirmation.
- Rule out a candidate only when a specific control or benign explanation is identified and shown to apply to the same reachable path before the relevant security-sensitive operation. Check its arguments, ordering, failure behavior, and alternate entrypoints. A safe sibling path, generic trust in a library, a 401/403, a failed request, or a missing prerequisite does not by itself rule it out.
- If evidence cannot confirm or rule out a plausible candidate, keep it inconclusive and state the exact proof gap. Blocked, unavailable, not-run, and out-of-scope work must retain that status with a reason; never mark it as passed or false positive.

### Severity calibration
- Rate severity only after establishing reachability, attacker prerequisites, the affected principal/data/action, and counterevidence. Apply the target program's policy and rating taxonomy first; distinguish confidence from impact and severity.
- Base the rating on demonstrated confidentiality, integrity, availability, privilege, and business impact. Do not raise severity for a secret-looking string, a public route, a scanner label, or a chain whose intermediate steps remain hypothetical.
- Reserve high/critical for demonstrated consequential impact across a meaningful trust boundary (for example, real sensitive cross-tenant access, privilege escalation, broadly reachable code execution, or credential exposure that is actually usable and grants meaningful access). Narrow prerequisites, limited scope, user interaction, and effective compensating controls should be reflected in the rationale.
- Record the reason for the chosen severity and the material limits of the proof. If impact remains unproven, report a candidate/inconclusive result rather than a confirmed high-impact vulnerability.

### Final report
Summarize what actually ran, meaningful counts, verified findings and candidates, canonical artifact paths, errors, and remaining work. Never claim complete coverage unless the saved evidence supports it.

# CyberStrike Recon

Do the reconnaissance work, do not narrate a plan. Use the existing canonical target workspace and saved scope. If the scope is already configured and unchanged, reuse it; do not repeatedly ask for confirmation or restart setup.

## Rules

- Keep authorization intact. Every concrete target request must pass the runtime's persisted scope checks. Do not bypass a refusal or broaden scope.
- Use the tools that best fit the current evidence and environment. Discover and combine available tools as useful; no fixed phase-to-tool allowlist and no requirement to run every tool in a catalog.
- Do not impose arbitrary time limits, result caps, source counts, attempt counts, or early-stop rules on useful reconnaissance. Continue until the useful work is done, the available sources are exhausted, the user stops you, or a genuine blocker remains.
- If a tool fails, preserve its partial results and try another suitable method. Do not repeat successful work without a reason.
- Use checkpoint records to remember progress, not to block ordinary recon tools. Do not stop because an earlier phase status is stale or an optional ledger is incomplete. Keep vulnerability testing separate: do not run it unless the user explicitly requests it.
- Save results directly into the existing target workspace. Maintain one normalized inventory per data type, merge and deduplicate results, and avoid temporary copies, per-tool files, per-host folders, and repetitive intel entries.
- Keep bulk host/URL/parameter data in files. Use concise intel notes only for meaningful findings or phase summaries.
- JavaScript is a priority: collect all reachable in-scope JavaScript assets, deduplicate by content/URL, analyze scripts and available source maps as inert text, and connect routes/endpoints, methods, parameters, headers, cookies, auth clues, and possible secrets. Redact secret values.
- Do not mark a phase complete merely because a command ended. Record real results, partial work, errors, and what remains. Do not require verbose per-source bookkeeping when a useful normalized inventory is already saved.

## Workflow

1. Reuse or initialize the canonical workspace and verify the saved scope once. Run the required starting-asset scope check only when the scope is new, changed, or unresolved.
2. Start subdomain discovery immediately. In parallel where practical, use available passive sources such as certificate transparency/crt.sh, subfinder, assetfinder, Amass, Findomain, and suitable public APIs. Merge each result as it arrives into one deduplicated `subdomains.txt`; never wait for every source or stop because one tool is missing.
3. Feed discovered hosts into available DNS/HTTP/TLS checks (for example dnsx, httpx, tlsx). Save one normalized `live-hosts.txt` and useful service metadata; do not repeat enumeration because a different phase label is active.
4. Collect URLs from live hosts with suitable available crawlers/history sources (for example katana, gau, waybackurls, or waymore). Use a crawler only when its invocation can preserve the current scope boundaries; generic-shell `hakrawler` and `gospider` invocations are intentionally refused until the runtime can enforce scope for each request. Merge results into one deduplicated `urls.txt`, then derive `parameters.txt`, API/auth/admin candidates, redirect candidates, and sensitive-file candidates locally.
5. Prioritize JavaScript: merge every discovered `.js`/ `.mjs`/ `.cjs` and relevant source-map URL from the URL collector, crawled/history URLs, HTML, other tool output, and any URLs the user supplies. Pass the merged URL list to `ingest_javascript_urls` with source provenance in batches of at most 500 URLs. The tool fetches and saves actual response bodies under the target-local `javascript/assets/`, checks the current persisted scope on each URL and redirect even when reusing cached files, reuses repeated URLs, and deduplicates identical content by SHA-256. If the result reports nonempty `metadata.pending_urls`, immediately call the tool again with the same `target_url` and `urls: []`; the manifest already persists the pending URLs and their provenance, so do not copy the same list back into the next call. Repeat until the pending list is empty. You may add newly discovered URLs (up to 500 per call) while resuming. The per-invocation byte budget is not a total-run cap. Analyze each unique content version once and inspect source maps as inert text. Then update the canonical root-level `javascript-analysis.md` with asset URLs/hashes, per-source-map status, analysis counts, redacted signal types, and unresolved gaps; update `endpoints.txt` with one record per normalized origin + method + path template, merging parameter/source/auth evidence instead of creating a row per parameter. Link detailed graph JSON under `javascript/` and candidate JSON under `endpoints/`; do not create competing inventories. Never claim complete JS coverage while any source URL is pending, skipped, failed, or not analyzed. Use suitable available analyzers as additional candidates, not mandatory tool assignments.
6. Check relevant historical sensitive-file URLs and exposed-file candidates where appropriate. Use directory/parameter fuzzers, port scanners, nuclei templates, or other active checks only when the program policy permits that activity and each request passes scope/rate/impact controls. Keep exploit-style or state-changing vulnerability tests opt-in.
7. Write/update `reports/recon-final.md` with actual counts, completed and partial work, useful findings, artifact paths, source failures, and remaining gaps.

The sequence is a practical guide, not a tool restriction. Use any suitable tool at any point when it helps close an evidence gap. Reuse existing results and continue from unfinished work.

## Final response

Give a concise status, meaningful counts, the workspace path, key findings, artifact paths, and genuine blockers only. Never claim exhaustive coverage without evidence.

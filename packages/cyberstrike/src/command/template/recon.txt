# CyberStrike Recon

Do the work, not a long plan in chat. Follow the numbered sequence and verify saved results. Use `.cyberstrike/skill/RECON_PHASE_TOOL_MATRIX.md` for the required artifact and completion check for each phase.

## Rules

1. **Scope:** keep the original CyberStrike scope/policy unchanged. For a new, changed, or unresolved target/policy, review and save it, then check the actual starting asset once. Reuse that decision on resume. The chosen tool must enforce scope for every actual request and redirect. Never broaden scope or switch tools to evade a refusal.
2. **Tools:** choose any suitable currently available tool/API/CLI/helper; inspect its schema when needed. Phase names are not a tool allowlist. Do not install or run every candidate.
3. **Coverage:** no arbitrary time, source, host, URL, result, or attempt caps. Merge useful partial results as they arrive. On failure, try a suitable alternative or record the real blocker; never invent output.
4. **Resume:** check `recon_checkpoint` and existing artifacts first. Reuse valid completed work; resume only unfinished items. Repair missing/invalid artifacts. A stale checkpoint must not prevent useful ordinary recon.
5. **One source of truth:** save to the existing root target workspace. Update canonical inventories; deduplicate without discarding meaningful method, path, parameter, source, or evidence differences. No per-host workspaces, temporary copies, or one file per tool.
6. **Testing:** findings and scanner alerts are leads, not proof. Do not run vulnerability scanners, `session_scan`, exploit payloads, or targeted vulnerability tests unless the user explicitly asks for testing and policy/runtime gates permit it.
7. **Completion:** for each phase, inspect state → do unfinished work → verify its required artifacts → update the checkpoint. Mark complete only when verified. Record blocked/unavailable/deferred reasons truthfully; only `vulnerability_testing` may be deferred.

## Workflow

0. **Resume and setup** — resolve or initialize the canonical root workspace only if missing; recover the run/checkpoint and existing files. Configure/check scope only if new, changed, or unresolved. If authorization is unclear, do not send active requests.

1. **`asset_discovery`** — enumerate seed-domain subdomains using useful available passive sources. Merge normalized unique hosts into `subdomains.txt`. A source failure must not stop other sources.

2. **`live_hosts_ports`** — validate candidates with suitable DNS/HTTP/TLS checks. Save `live-hosts.txt`; save `ports.txt` only when port checks were performed and permitted. Discovery does not grant authorization.

3. **`url_collection`** — collect URLs from crawlers, sitemaps, application/HTML links, captures, history, API descriptions, other collectors, and user input. Merge into `urls.txt`. Keep JS/module/source-map URLs and sensitive-file candidates; collect JS candidates as soon as they appear.

4. **`directory_fuzzing`** — perform permitted, non-destructive path discovery with a suitable tool/wordlist. Merge new URLs into `urls.txt`; review sensitive-file candidates. Do not create a duplicate URL inventory.

5. **`parameter_discovery`** — derive parameters from URLs, forms, captured requests/responses, API descriptions, and JS evidence. Merge into `parameters.txt`; mark each as observed or inferred.

6. **`parameter_fuzzing`** — only perform permitted low-impact discovery checks, one variable at a time, with a baseline/control. Save results to `parameter-tests.md` or existing `parameters/` evidence. No exploit payloads here. If unavailable/not permitted, record why and continue.

7. **`javascript_analysis` — priority** — gather JS candidates from **all sources**, including user-provided links, `urls.txt`, crawlers/history, HTML/imports, captured traffic, extensionless JavaScript responses, and source maps. Use `ingest_javascript_urls` when suitable, or an equivalent verified scope-enforced collector; reuse content by URL/hash. Analyze each unique version as inert data—never execute scripts/maps. Use `correlate_javascript` when suitable, or an equivalent analyzer. Merge endpoint/method/path, parameters, source locations, auth/header/cookie/role/feature clues, and redacted secret fingerprints. Record incomplete/pending/out-of-scope/malformed/truncated source maps honestly. Save `javascript-analysis.md` and update `endpoints.txt`.

8. **`endpoint_inventory`** — merge endpoint evidence from URLs, JS/maps, captures, API descriptions, and existing inventories. One identity per **origin + HTTP method + normalized path template**; query parameters alone do not create duplicate endpoints. Merge parameter/source/auth evidence and verify `endpoints.txt`.

9. **`vulnerability_testing`** — if not explicitly requested, defer this phase and continue to reporting. If requested, require completed endpoint inventory and passed scope/policy/runtime checks. Test one controlled change against a baseline/control; save actual redacted evidence and validate before claiming a finding.

10. **`reporting`** — update `reports/recon-final.md` from saved artifacts/checkpoints. Verify artifact paths and actual counts. Report what was discovered, fetched, analyzed, inferred, tested, confirmed, failed, or remains unresolved; include blockers and the precise resume point. Never claim exhaustive coverage without evidence.

Use any suitable tool when it closes a real evidence gap; the sequence defines workflow, not tool restrictions. Do not skip a phase or repeat successful work just to increase activity.

## Final response

Be brief: status, workspace path, verified counts, report/artifact paths, meaningful evidence, and real blockers only.

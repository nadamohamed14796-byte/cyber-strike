## Rules

1. The canonical workspace is intentionally compact: init guarantees only scope/, assets/, and runs/. Before shell redirection writes into recon/, javascript/, findings/, reports/, or any nested scratch path, create the parent directory under the exact returned workspace path (for example, mkdir -p -- "$WORKSPACE/recon"). Prefer stdout plus target_artifact for canonical outputs. Never assume an output folder exists or let a redirection failure masquerade as a scanner failure.
2. On a command failure or aborted tool call, inspect the exit status, stderr, process state, and any partial artifact before deciding what to do. Preserve useful partial output. Do not repeat an unchanged command after a deterministic error; fix the actual cause, resume remaining work, or switch to a materially different method. Do not discard stderr before diagnosing a failed collector.
3. Follow the shared Target Workflow Contract for scope, workspace, tool choice, safety, caps, failure handling, and completion. This template defines recon-specific phases and outputs; it must not create competing global rules.
4. Keep progress tracking lightweight. Reuse the existing workspace and checkpoint when available; update phase status when useful, but never let a phase label, stale checkpoint, rejected `begin`, or already-resolved marker stop ordinary reconnaissance or force you to repeat work. Checkpoint errors affect the progress record, not whether a suitable ordinary recon tool may run. Persist and verify results in the canonical workspace. Only targeted vulnerability testing remains opt-in and requires authorization, policy, and endpoint evidence.

## Evidence-driven Strix-style tool and skill selection

- Search the actual skill/tool registry by the current evidence gap and required output, not by a fixed executable name. Discover relevant registered tools, installed CLIs, helpers, APIs, and datasets dynamically; inspect their schemas/help and load only the relevant skills. Tool examples in references are candidates, not requirements, and do not imply that the executable is installed.
- Before using any CLI for the first time in this run, verify its identity, version, current help output, supported target/list syntax, coverage flags, output format, and side effects once per executable version. Resolve naming collisions from the actual binary and help text. Parse that tool's documented output schema; do not infer output structure from a sample prefix.
- For passive asset discovery, do not default to a fixed pair or fixed list of tools. Find the relevant available sources by capability, compare independent coverage, and run each useful, available, non-redundant source that fits authorization, configuration, and rate constraints. Inspect each CLI's current help and use its own broad-source, recursive, input-list, and output flags only when that installed version supports them. Such flags are tool-specific and provider configuration affects actual coverage; never copy or guess options. If a valid target syntax is rejected as missing a target, diagnose the generic executor/parser path rather than abandoning the source. Preserve provider/API-key errors and zero-result sources separately.
- For crawlers, constrain scope to the authorized hostname set, set explicit depth/time/concurrency/rate controls, and emit a compact URL field when raw response bodies are unnecessary. Merge crawler results with HTML/script links, sitemaps, archives, and API specs; never let one source overwrite the others.
- Run independent passive sources in parallel only when the runtime supports real parallel execution. Stage each output, normalize it, scope-check candidates, and merge once. Use dynamic delegation only when a real task/subagent tool exists and each task has a measurable independent outcome.
- After each tool returns, verify exit status, stderr, output path, non-empty/explicit-zero semantics, and newly added unique records. If no progress, change the cause being tested (source, flags, input batch, parser, or tool) instead of rerunning the same command. A command aborted by the runtime is not proof that the child process stopped; inspect live processes and saved partial output before resuming, and never launch a duplicate long-running collector without checking.

## Completion and resume contract

- **Loop recovery:** on the first repeated-call/no-progress warning, allow one recovery turn with tools available. The agent must inspect prior results, change the failing cause or method, or advance independent work. Only continued repetition after that recovery may force a tool-free terminal wrap-up. Never make the user say “continue” to resume routine work.
- You may run any useful ordinary recon tool when its evidence is relevant; phase labels do not restrict tool choice. Do not mark a phase complete while its own required operation or canonical artifacts are missing. A prior phase marked `failed` or `blocked` with a concrete reason must not stall independent later work: preserve that status, continue unrelated collectors, and record the coverage gap in the final report. Scope validation and workspace setup must be complete before discovery; endpoint inventory must be complete before explicitly requested vulnerability testing. A rejected completion is a real unfinished item: fix the named artifact problem instead of ignoring the rejection and reporting success. In particular, if recon_checkpoint(action="complete") returns summary_required, retry that same completion with a concise summary grounded in verified scope/workspace state; do not start the next dependent phase until the checkpoint confirms saved: true. If it reports missing artifacts or prerequisites, repair those exact gaps and retry rather than skipping ahead.
- **Do not pipe discovered targets directly into a network-capable CLI.** Dynamic stdin can hide concrete targets from the executor's scope checks. Save producer output into the target workspace, normalize and validate every line against persisted scope, then pass the verified file using the receiving CLI's discovered and supported target-list flag. Use pipelines freely for local text-only operations such as sorting/deduplication after collection. If a network-capable CLI is rejected for missing explicit targets, switch to staged, scope-checked input instead of retrying the same pipeline.
- When a recon capability needs a missing CLI, select a maintained tool from the shared `TOOLING_CATALOG`, verify its official installation path and current flags, then use `ensure_tools` for that selected tool. Do not auto-install legacy commands copied from historical skills. Install an exact named tool only when the user explicitly requires it or a real format/behavior dependency demands it. If installation fails, preserve the exact blocker and continue independent work.
- `unavailable` and `deferred` are resumable, not permanent success. When reopened, downstream phase checkpoints are invalidated; re-check their artifacts and regenerate stale handoffs/reports before finishing.
- Before each phase completion, reconcile the actual sources attempted, raw output files, canonical merged inventory, and errors. A planned command, a tool call, a non-empty file, or an agent's verbal claim is not proof that the method succeeded. Continue while a concrete useful step remains, and report exact pending items if execution must pause.

## Adaptive execution and delegation

- When a real Task/delegation tool is available, parallelize only independent work that benefits from it. Give each worker a bounded input, the canonical root `target_url`, the same persisted scope constraints, a clear evidence/provenance contract, and one non-overlapping responsibility.
- Keep one orchestrator responsible for scope, `recon_checkpoint`, JavaScript ingestion/manifest writes, and final inventory merging. Do not run concurrent writers against the same target-local manifest or canonical inventory. Workers may perform independent read-only analysis or collect candidate inputs, then return verified observations, source/tool, counts, artifact paths, errors, and unresolved items; they must not create child workspaces, change scope, overwrite shared canonical inventories, or promote hypotheses to confirmed findings.
- Continue useful independent work while workers run. Wait only when a next decision actually depends on their results. If delegation is unavailable, perform the task directly rather than stalling. Stop or redirect redundant work instead of running duplicate tools for activity.
- Merge partial results into the existing canonical inventory, normalize and deduplicate once, and preserve provenance and failures. After worker completion, reconcile the checkpoint against the actual saved artifacts; a worker's message alone is not proof that an artifact exists.
- **Inventory merge integrity (mandatory):** before finalizing, enumerate candidate files recursively under the canonical root inventories, `recon/`, `scope/`, `assets/`, `javascript/`, and `findings/` paths. Include every relevant successful/partial collector output, not just files matching one suffix. Keep raw files unchanged; build canonical lists from all eligible sources with per-item provenance. Parse each tool's actual documented output format instead of assuming a prefix or line format; classify successful responses separately from failures/timeouts and verify the canonical list against raw output.
- **Canonical inventory format (mandatory):** `subdomains.txt` contains one normalized DNS hostname per line (wildcards may be normalized to their base hostname), `live-hosts.txt` contains one verified live hostname/host:port per line, `urls.txt` contains one absolute HTTP(S) URL per line, and `parameters.txt` contains one normalized parameter record per line. Do not put tool banners, JSON logs, progress text, errors, timeout messages, or `[FAILED]` rows into these canonical files; keep those in raw logs and track their status separately. Deduplicate canonical rows before marking completion. If a phase genuinely finds nothing, use a single explicit status such as `status: zero-results` or `incomplete: <reason>` instead of inventing a result or leaving the file blank. These formats are validated by `recon_checkpoint`; repair invalid output instead of retrying the same merge unchanged.
- **Count-to-artifact consistency (mandatory):** calculate each reported count from the exact canonical artifact that the report names; record raw candidate count, unique normalized count, verified count, failed count, and pending count separately where applicable. Cross-check that every reported live host is present in `live-hosts.txt`, every reported URL is present in `urls.txt`, and every reported JS asset is represented in the JS manifest with a real downloaded file or an explicit non-downloaded status. If the canonical file is empty, malformed, unreadable, or inconsistent with the claimed count, do not claim success or write a success summary; repair the merge or mark the phase failed/incomplete with the concrete reason.
- Close each recon work item as verified-result, empty, failed, blocked, unavailable, or pending. For vulnerability hypotheses, use confirmed, ruled-out, inconclusive, blocked, or not-run; only the existing evidence/validation lifecycle may confirm a finding. During ordinary recon, keep hypotheses as leads and obey Rule 5.
- **Batch and timeout:** split independent root domains into separate tasks and split large host lists into bounded batches (for example, 5–10 hosts per worker when that fits the tool). Set a real timeout/deadline when the execution interface supports it. Do not wait for one huge worker to finish before saving or progressing other independent work.
- **Checkpoint each result:** after every batch or meaningful tool result, persist the counts, source/tool, output path, errors, and next action in the existing checkpoint or target notes. On restart, inspect saved outputs and resume the first incomplete item; never restart the entire phase just because a later step failed.

## Strix-inspired asset discovery rules

Strix's recon skill improves coverage by combining certificate transparency, live TLS SAN extraction, passive DNS, and (only when scope/ownership supports it) ASN/IP clues instead of trusting one enumerator. Apply the useful pattern without importing Strix's assumption that every related asset is in scope:

- **Source diversity:** compare CT, subdomain tools, DNS records, crawler-discovered hostnames, and configured passive APIs. Report each source as success, zero-results, failed, blocked, or not configured.
- **TLS feedback loop:** after scope-checking and probing eligible hosts, collect certificate CN/SAN values; normalize them and feed only newly eligible names back into discovery. Record certificate fingerprints only as correlation evidence, not ownership proof.
- **DNS pivots:** retain A/AAAA/CNAME and PTR relationships where available. A shared IP or CNAME provider is not sufficient to claim a neighboring hostname belongs to the target.
- **Asset classification:** classify verified live hosts by observed evidence (web app, API, auth, staging, admin/observability, storage, mail, or non-HTTP service). Include the evidence/source and confidence; do not infer technology or ownership from hostname alone.
- **Coverage reconciliation:** compare candidates → scope-eligible candidates → resolved → live HTTP/TLS → checked ports. Keep these counts distinct so passive candidates are never reported as live hosts.
- **Bounded parallelism:** parallelize independent domains/sources and keep the root agent responsible for scope, canonical files, deduplication, and completion. A worker must return artifact path, exact counts, tool/source, exit status, errors, and unresolved leads; a status message alone is not evidence.
- **No-progress recovery:** if a source/tool fails, preserve stderr and exit status, verify tool identity/help once, then switch to a materially different source or technique. Do not repeat an unchanged command or wait indefinitely for a loop that adds no assets. Save partial results before moving to independent work.

## Workflow

0. **Resume setup:** reuse the existing workspace and verified artifacts. Confirm the saved scope manifest is configured; each active request must still pass request-level scope enforcement. Do not rerun completed work without a concrete reason.

1. **`asset_discovery` — multi-source expansion:** start with the exact supplied in-scope seed domains and reuse any verified inventory. Dynamically discover all relevant registered sources, installed CLIs, existing helpers, and reachable passive APIs/datasets. Compare their actual capabilities and configuration, then run useful, independent, non-redundant sources in parallel when supported; do not limit collection to named examples or a fixed number of tools. Capture source/tool/version, exact redacted invocation, exit status, counts, and source-specific errors. Normalize case/trailing dots/wildcards and merge one canonical hostname per line into root `subdomains.txt`, retaining useful provenance. Do not count provider/CDN aliases, historical-only names, or unverified siblings as confirmed owned assets.

   **Iterative pivots (the key Strix pattern):** every newly observed in-scope hostname is a seed for appropriate next checks: DNS A/AAAA/CNAME (preserve CNAME chains), TLS certificate CN/SAN on verified live TLS endpoints, and passive DNS/CT lookups where available. Harvest SAN names and PTR/CNAME leads, normalize and deduplicate them, then feed only newly added candidates into the next iteration. Use a convergence check based on the unique candidate set: continue while an iteration adds new eligible assets or a materially different source remains untried; stop when two consecutive eligible passes add zero new candidates, or when all useful sources are exhausted. Never repeat an unchanged query after a deterministic failure; change source/method or record the exact blocker. This is a convergence rule, not a fixed cap on the number of assets.

   **Attribution and scope:** a CT/SAN/PTR/ASN result is a lead, not proof of ownership or permission. Before any request/scanner touches a candidate, normalize it and validate it through the existing persisted scope rules. Do not silently expand the user's scope to sibling domains, ASN ranges, shared IP neighbors, or third-party CNAME providers. Keep out-of-scope or ambiguous leads in a separate evidence note with the reason, not in active target inventories. Only enumerate IP ranges when the supplied scope explicitly covers them or the existing scope matcher approves each concrete target.

   Run separate root-domain jobs when independent; avoid duplicate work across workers. Use workers only for independent source collection/pivoting, with one orchestrator owning the canonical inventory and final merge. Keep raw evidence intact; merge normalized results once, dedupe, and preserve source provenance and source-specific failures.

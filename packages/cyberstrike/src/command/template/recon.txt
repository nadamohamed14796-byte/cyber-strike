# CyberStrike Recon

Do the work, not a long plan in chat. Follow these steps, save results, verify them, and report only verified outcomes. Use the phase matrix when it is available in the repository or installed skill assets; never assume a relative path exists in the target workspace. The steps below define the required artifacts if that reference is unavailable; `recon_checkpoint` stores progress.

## Rules

1. Follow the shared Target Workflow Contract for scope, workspace, tool choice, safety, caps, failure handling, and completion. This template defines recon-specific phases and outputs; it must not create competing global rules.
2. Keep progress tracking lightweight. Reuse the existing workspace and checkpoint when available; update phase status when useful, but never let a phase label, stale checkpoint, rejected `begin`, or already-resolved marker stop ordinary reconnaissance or force you to repeat work. Checkpoint errors affect the progress record, not whether a suitable ordinary recon tool may run. Persist and verify results in the canonical workspace. Only targeted vulnerability testing remains opt-in and requires authorization, policy, and endpoint evidence.

## Adaptive execution and delegation

- When a real Task/delegation tool is available, parallelize only independent work that benefits from it. Give each worker a bounded input, the canonical root `target_url`, the same persisted scope constraints, a clear evidence/provenance contract, and one non-overlapping responsibility.
- Keep one orchestrator responsible for scope, `recon_checkpoint`, JavaScript ingestion/manifest writes, and final inventory merging. Do not run concurrent writers against the same target-local manifest or canonical inventory. Workers may perform independent read-only analysis or collect candidate inputs, then return verified observations, source/tool, counts, artifact paths, errors, and unresolved items; they must not create child workspaces, change scope, overwrite shared canonical inventories, or promote hypotheses to confirmed findings.
- Continue useful independent work while workers run. Wait only when a next decision actually depends on their results. If delegation is unavailable, perform the task directly rather than stalling. Stop or redirect redundant work instead of running duplicate tools for activity.
- Merge partial results into the existing canonical inventory, normalize and deduplicate once, and preserve provenance and failures. After worker completion, reconcile the checkpoint against the actual saved artifacts; a worker's message alone is not proof that an artifact exists.
- Close each recon work item as verified-result, empty, failed, blocked, unavailable, or pending. For vulnerability hypotheses, use confirmed, ruled-out, inconclusive, blocked, or not-run; only the existing evidence/validation lifecycle may confirm a finding. During ordinary recon, keep hypotheses as leads and obey Rule 5.
- **Batch and timeout:** split independent root domains into separate tasks and split large host lists into bounded batches (for example, 5–10 hosts per worker when that fits the tool). Set a real timeout/deadline when the execution interface supports it. Do not wait for one huge worker to finish before saving or progressing other independent work.
- **Checkpoint each result:** after every batch or meaningful tool result, persist the counts, source/tool, output path, errors, and next action in the existing checkpoint or target notes. On restart, inspect saved outputs and resume the first incomplete item; never restart the entire phase just because a later step failed.

## Workflow

0. **Resume setup:** reuse the existing workspace and verified artifacts. Confirm the saved scope manifest is configured; each active request must still pass request-level scope enforcement. Do not rerun completed work without a concrete reason.

1. **`asset_discovery`:** enumerate seed subdomains using useful passive sources (CT, `subfinder`, Amass, assetfinder, APIs). Merge normalized unique hosts into root `subdomains.txt`; preserve partial results and source failures. Run separate root-domain jobs when independent; do not combine unrelated domains into one oversized task.

2. **`live_hosts_ports`:** process each candidate with suitable DNS/HTTP/TLS checks; record results/errors. Save root `live-hosts.txt`; save `ports.txt` only if port checks ran and were permitted. Unprocessed does not mean dead or in scope.

3. **`url_collection`:** collect from every eligible in-scope host using useful crawlers, sitemaps, app/HTML links, captures, history, API descriptions, other collectors, and user input. Split inputs if a tool accepts one URL only. Merge into root `urls.txt`; remove exact duplicates but preserve meaningful method/path/query variants. Gather JS, source maps, API/auth routes, and sensitive-file candidates as soon as found. Track source/input as success, empty, failed, or pending. Check per-host coverage immediately; a host with zero URLs is a coverage gap to investigate, not automatic proof that no URLs exist.

4. **`directory_fuzzing`:** use suitable non-destructive path discovery only when permitted. Merge paths into `urls.txt`; save `directories/path-discovery.md` with target, tool/version, wordlist+hash, method/rate/settings, counts, exclusions, errors, and useful response fingerprints. If blocked/inapplicable, mark unavailable with a reason.

5. **`parameter_discovery`:** derive parameters from URLs, forms, captures, API descriptions, and JS first. Use tools only to close a real gap and when permitted. Merge into root `parameters.txt`; include endpoint/method/location/source and observed-vs-inferred status.

6. **`parameter_fuzzing`:** only low-impact, permitted discovery checks; use a baseline/control and change one variable at a time, no exploit payloads. Save root `parameter-tests.md` with settings/results or a truthful blocked/not-applicable reason.

7. **`javascript_analysis` (priority):**
   - **Discover live assets first.** Fetch/inspect the current in-scope HTML response and extract script `src`, module/preload references, inline scripts, and relevant import/source-map references. Resolve relative URLs against the final page URL. Then inspect live crawler/capture/URL-collector results and extensionless responses that appear to be JavaScript.
   - **Use history as a supplement, not the live-source-of-truth.** Historical archives may add leads or reveal old routes, but hashed filenames and archived URLs are not assumed to be live. Before ingesting a historical candidate, validate it through the normal scope-enforced fetch path. A failed archived URL must not be retried via another tool or rewritten script unless new evidence or a changed hypothesis justifies it.
   - Gather candidates from all eligible sources—`urls.txt`, crawlers/history, HTML/imports, captures, other collectors, user links, extensionless JS responses, and source maps. Submit eligible URLs with provenance to `ingest_javascript_urls` or an equivalent scope-enforced collector; track each as fetched, dedup/cache hit, out of scope, failed, skipped, or pending. Never bypass scope.
   - Before writing/running an analyzer, verify the input directory and manifest contain actual downloaded assets; inspect counts, file sizes, content type, and a small sample. Exclude notes, empty files, HTML error pages, and metadata from code-only scans, while still parsing HTML as an inert container for script references. Do not create a large script when no valid input exists.
   - If the tool reports `metadata.pending_assets > 0`, resume with the same `target_url` and `urls: []`; the manifest retains pending assets and their provenance, so do not repeatedly resend the full URL list. Continue while pending work remains and each invocation makes progress; preserve exact failures instead of looping on unchanged retryable errors.
   - Analyze each unique URL/content version and source maps as inert text; never execute them. Use `correlate_javascript` or an equivalent verified analyzer. Extract endpoint/method/path, parameters, source locations, auth/header/cookie/role/feature clues, and redacted secret fingerprints—never raw secret-like values.
   - For scripts you create, use small increments; run `bash -n` for Bash and `python -m py_compile` for Python before real execution, then test on a small sample. For files above roughly 500 KB–1 MB, use bounded targeted searches and structured extraction instead of printing the entire file or forwarding huge output into chat. Delegate only if a real delegation tool is available and useful.
   - Preserve raw scope-checked captured responses only as sensitive target-local evidence under `javascript/captured/` with `javascript/captured-index.json`; keep summaries and endpoint inventories redacted. Track pending/out-of-scope/missing/partial/malformed/truncated maps honestly. Verify the canonical root `javascript-analysis.md` and `endpoints.txt` exist, contain the merged inventory, and distinguish zero-result from incomplete status; supporting evidence goes under `javascript/` and `endpoints/`.

8. **`endpoint_inventory`:** merge URL, JS/map, capture, API, and saved evidence into root `endpoints.txt`. One identity per **origin + method + normalized path template**; query parameters alone don't create duplicate rows. Merge parameter/source/auth evidence. Record an explicit zero-result status if none were found.

9. **`vulnerability_testing`:** if not explicitly requested, begin then defer with reason and continue. If requested, require completed endpoint inventory plus passed scope/policy/runtime controls. Use baseline/control and one controlled change at a time. Save root `findings.md` and redacted evidence under `testing/`, `findings/`, or `evidence/`. Validate before claiming a finding; if safe testing cannot proceed, record the actual blocker.

10. **`reporting`:** create/update root `reports/recon-final.md` from saved artifacts/checkpoints. Verify artifact paths and counts. Distinguish discovered, in-scope, fetched, analyzed, inferred, tested, confirmed, failed, and unresolved. Include source failures, limitations, and the exact resume point. Never claim exhaustive coverage without evidence.

Use the sequence as a convenient checklist, not a lock. Choose tools from the current evidence gap and actual availability, including tools commonly associated with another phase. Do not call a tool merely to satisfy a phase, and do not stop useful work because a checkpoint is stale or rejects a progress update. Keep scope enforcement, non-destructive defaults, and explicit opt-in for vulnerability testing.

## Final response

Keep it brief: status, workspace path, verified counts, report/artifact paths, useful evidence, and real blockers only.

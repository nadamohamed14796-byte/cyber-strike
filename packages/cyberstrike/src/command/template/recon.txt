# CyberStrike Recon

Run recon continuously. Reuse the existing target workspace and completed evidence; do not narrate a plan or restart finished work.

## Rules
- Use the original persisted scope rules. Check the starting asset once for a new, changed, or unresolved scope; every concrete request and redirect must still pass runtime scope enforcement.
- Choose any suitable available tool at any phase. Phase names, skill files, and tool catalogs are guidance, not tool allowlists. A missing tool or stale checkpoint must not stop ordinary recon.
- Do not add arbitrary total time, result, source, or attempt limits. Preserve partial results and continue with suitable alternatives when a source fails.
- Keep one canonical inventory per data type in the target workspace. Merge and deduplicate as results arrive; avoid duplicate reports, per-tool output files, and unnecessary folders.
- Treat static clues as leads. Do not execute downloaded JavaScript or run vulnerability-oriented tests unless the user explicitly requests testing and scope, policy, and testing checkpoints permit it.

## Workflow
1. **Resume and scope:** Reuse the root target workspace and saved progress. Initialize only if missing. If scope is new, changed, or unresolved, validate the actual starting asset once; never infer or broaden scope.
2. **Find subdomains:** Start passive discovery immediately using suitable available sources (for example, certificate transparency, `subfinder`, Amass, or public APIs). Merge results into `subdomains.txt` as they arrive. Continue if any source fails.
3. **Find live hosts and URLs:** Use suitable DNS/HTTP/TLS checks and save `live-hosts.txt`. Collect eligible crawler, archive, and application URLs into `urls.txt`; derive `parameters.txt` and relevant API, auth, redirect, and sensitive-file candidates. Use only crawler invocations that preserve request-level scope boundaries.
4. **Collect and analyze JavaScript first:** Gather every eligible `.js`, `.mjs`, `.cjs`, and relevant source-map URL from all collectors, crawlers, HTML, other tools, and user-supplied links. Send URLs with provenance to `ingest_javascript_urls` in batches of up to 500. It downloads actual response bodies, checks each URL and redirect against persisted scope, and deduplicates identical content by SHA-256.
   - If `metadata.pending_urls` is nonempty, call `ingest_javascript_urls` again for the same target with `urls: []`. The manifest already stores the pending queue and provenance; do not resubmit the same URLs. Repeat until the pending queue is empty. The per-call byte budget is not a total-run cap.
   - Run `correlate_javascript` after ingestion. Verify the generated root-level `javascript-analysis.md` and `endpoints.txt`. Keep one endpoint per normalized origin + method + path template, merging parameter, source, header/cookie, and auth evidence. Preserve detailed evidence under the existing `javascript/` and `endpoints/` areas.
   - Analyze downloaded code and source maps as inert text only. Record source-map references as analyzed, pending, out-of-scope, or incomplete. Do not claim full coverage while any URL or map remains pending, skipped, failed, truncated, or unanalyzed.
5. **Close recon gaps:** Review historical sensitive-file URLs and exposed-file candidates. Use directory/parameter discovery, port scans, and other active recon only when program policy and request-level controls allow it. Do not turn static leads into vulnerability tests automatically.
6. **Report and resume:** Update `reports/recon-final.md` with verified counts, artifact paths, useful leads, source failures, incomplete work, and the next resume point. Verify files before marking work complete.

## Final response
Give a concise status, actual counts, workspace path, important leads, artifact paths, and genuine blockers only.

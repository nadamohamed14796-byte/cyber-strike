# HTTP 401/403 Access-Control Assessment

## When to use

Use when an in-scope route returns 401/403 and there is a concrete hypothesis that authentication, routing, proxy normalization, or role enforcement differs across equivalent requests.

## Safety gate

Do not brute-force paths, probe unrelated hosts, or bypass access controls to retrieve sensitive data. Start with a known route and harmless resource. Stop immediately if the response exposes private data.

## Procedure

1. Capture the original request, response, authentication state, and expected policy.
2. Compare only plausible, documented equivalents: trailing slash, case normalization, URL encoding, supported content type, and known reverse-proxy route mapping.
3. If method differences are in scope, compare a safe read-only request across supported methods; never issue destructive methods.
4. Check whether the response is generated by the application, gateway, WAF, or CDN. Preserve headers and body clues.
5. For role-bound routes, compare two controlled accounts with different permissions and a harmless resource.
6. Validate any discrepancy using a second request and confirm meaningful access, not only a changed status code.
7. Record the exact normalization or trust boundary that caused the difference and stop at minimum proof.

## Pitfalls

- 401 and 403 can be intentionally different.
- WAF or CDN responses may not reflect origin authorization.
- Encoded-path variants can have operational impact; use only a few low-rate probes.
- A 200 response may still contain an error page or no sensitive content.

## Verification

A finding requires a reproducible policy violation and semantic access to a protected resource or operation. Status-code changes alone are leads, not confirmed vulnerabilities.

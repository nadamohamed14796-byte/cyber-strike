# Recon Phase Matrix: State, Artifacts, and Completion

This matrix defines phase objectives, dependencies, canonical outputs, and completion checks—not tool assignments or runtime state. The workflow lives in `packages/cyberstrike/src/command/template/recon.txt`; `recon_checkpoint` owns resumable progress and runtime transitions; `recon-master/SKILL.md` selects the relevant procedure from its `RECON_CHAPTERS.md` companion; and `community-tool-selection` owns the shared, non-exhaustive `TOOLING_CATALOG.md` tool/helper reference. Other specialist skills own vulnerability-class validation after an evidence-backed handoff.

At every checkpoint, choose any suitable available tool based on the evidence gap, capability, saved results, runtime, and policy. This matrix is not a tool allowlist, and stale phase state must not block useful ordinary recon. Preserve request-level scope enforcement and explicit opt-in for parameter fuzzing and vulnerability testing. Bare filenames below are canonical root inventories unless an output area is named; compact folders hold supporting raw/structured evidence, not duplicate normalized inventories. The standard output folders are `scope/`, `assets/`, `runs/`, `recon/`, `javascript/`, `findings/`, and `reports/`; endpoint sidecars and legacy endpoint artifacts go under `recon/`, not a separate `endpoints/` folder. If this guidance conflicts with runtime validation, follow the runtime contract and reconcile the documentation.

## Phase matrix

| Canonical phase | Required saved artifact(s) | Completion condition | Boundary / dependency |
|---|---|---|---|
| `scope_validation` | Runtime-generated `scope/scope.json` authorization manifest and any imported scope snapshots | Preserve the authoritative policy/source, include/exclude rules, unsupported entries, decision, and ambiguity. Validate the canonical starting asset once during initial setup and reuse the saved decision while target/policy are unchanged. Do not create a duplicate root-level `scope.txt`. | Must precede active work. A workspace is not authorization; each concrete request and redirect still passes runtime scope enforcement. |
| `workspace_setup` | Verified canonical workspace and its initialized run state | Confirm only the core `scope/`, `assets/`, and `runs/` directories plus required manifests/checkpoint; output folders are created on demand. | Initialize once and resume the same workspace for the same program/root. Never guess an output directory. |
| `asset_discovery` | `subdomains.txt` | Save normalized, deduplicated hostnames immediately. Preserve partial results and continue when any source fails. | Use suitable available sources; do not wait for every source to finish before moving on. |
| `live_hosts_ports` | `live-hosts.txt`; `ports.txt` when a permitted port/service check is actually run | Preserve DNS/HTTP/TLS/service evidence, response status, timestamps, errors, and raw-versus-normalized distinction; verify counts and paths. | `live-hosts.txt` is the required completion artifact; `ports.txt` is conditional evidence, not a blanket phase gate. DNS or HTTP liveness does not prove scope or a vulnerability. Run port checks only when program policy allows. |
| `url_collection` | `urls.txt` | Process every eligible in-scope host using suitable available crawling/API/history sources; retain per-input/source result states, deduplicate exact identities, and preserve meaningful parameter/method variants. | Never weaken request-level scope checks or send a multi-host list to a tool that accepts one URL. Reuse verified results when inputs and tool versions are unchanged. |
| `javascript_analysis` | `javascript-analysis.md`, `endpoints.txt`; detailed evidence under `javascript/`, `recon/`, or `findings/` only when useful | Analyze each distinct bundle version once using URL plus content hash; correlate request/capture IDs, routes, methods, parameters, source locations, auth/header/cookie clues, browser-boundary signals, and available source/lockfile evidence. Parse captured version-3 source maps and analyze available `sourcesContent` entries without saving source text; record every external `sourceMappingURL` with analyzed/pending/out-of-scope/incomplete status. Persist scope-checked captured JS/source-map response bodies under `javascript/captured/` and index them in `javascript/captured-index.json`; treat raw assets as sensitive local evidence. Verify canonical summaries and artifact paths, and do not complete JavaScript analysis without verified non-empty source evidence or an evidence-backed unavailable status. | Runs immediately after URL collection, before parameter/path discovery. Do not execute untrusted JavaScript or source maps. Retain secret fingerprints and source locations, not raw candidate values. A map with missing or partial embedded sources, malformed JSON, or truncation is incomplete, not complete. Findings require separate validation. |
| `parameter_discovery` | `parameters.txt` | Record parameter name/location, endpoint template, method, source, auth/content-type context, confidence, and observed-versus-inferred state. | Derive from URLs, forms, JS traces, API descriptions, and captures first; use an additional discovery tool only to close a real evidence gap when authorized. |
| `directory_fuzzing` | Canonical path inventory/evidence in the permitted workspace | Record the selected source/wordlist and hash, target, method, request/rate settings, outcome, exclusions, and relevant response fingerprints. | Runs after JS and parameter evidence are merged. Only if policy permits; keep rate/impact bounded. This phase is not a blanket requirement to run every directory tool. |
| `endpoint_inventory` | `endpoints.txt` | Normalize to one endpoint record per origin + route template + API version, with HTTP methods nested as separate operations. Persist Agent-discovered updates through `target_endpoint`; do not create one endpoint note per method. Merge source/provenance into the matching operation while keeping each method's parameter locations, headers, content types, auth context, and response evidence separate. Compare contract-declared, JavaScript-declared, and traffic-observed operations explicitly; do not label traffic-only methods as JavaScript-declared. Verify endpoint-root and operation counts. | Requires resolved JavaScript, parameter-discovery, and path-discovery evidence. Mandatory before either active-testing phase. Avoid duplicate endpoint rows caused solely by multiple parameters. |
| `parameter_fuzzing` | `parameter-tests.md` | Preserve baseline, single-variable request change, settings, response comparison, negative controls, result, and stop condition. | Explicit opt-in only; do not begin until scope/workspace and endpoint inventory are complete. No uncontrolled brute force, exploit payloads, or repeated state-changing requests. Leave pending when not requested. |
| `vulnerability_testing` | `findings.md` and linked evidence when testing is explicitly requested | Each candidate has a hypothesis, preconditions, baseline/control, minimally impactful test, request/response evidence, validation status, limitations, and stop condition. | Do not begin before endpoint inventory. For a recon-only run, defer this phase with an explicit reason and continue to reporting. |
| `reporting` | `reports/recon-final.md` | Verify report and evidence paths, redaction, reproduction detail, impact/limitations, truthful phase/source counts, and precise blockers/resume point. | The report must match the persisted ledgers; never claim completion while required work remains pending. Optional parameter fuzzing and vulnerability testing may remain pending when the user did not request active testing. |

## Source and phase status

Source failures and stale phase state must not block ordinary recon. Verify the canonical inventory and continue from available evidence.

When a capability is missing, select a suitable available alternative if one closes the same evidence gap. Phase/checkpoint state must never block ordinary tool execution or tool selection: run any suitable available tool at any recon phase, then record its evidence under the appropriate phase and reconcile progress afterward. Checkpoint transitions are separate: do not skip failed/blocked prerequisites; repair them, mark them unavailable with a concrete reason when genuinely unavailable, or record a reasoned partial handoff with an evidence-backed summary. A partial handoff resolves dependency ordering but never claims full completion. Record a precise unavailable/blocked reason only when the capability is genuinely unavailable or a concrete runtime, authorization, scope, or policy check rejects that action. Never invent results, weaken scope enforcement, or report a missing source as successful.

# Host Header Injection Assessment

## Objective

Determine whether the application or an intermediary trusts attacker-controlled `Host`, `X-Forwarded-Host`, `X-Forwarded-Proto`, or related metadata when routing requests or generating security-sensitive absolute URLs.

## Scope and safety

Do not trigger password resets for real users, collect reset links, or send crafted links to anyone. Use a dedicated account and inspect only the resulting test message or a staging mail sink. Do not probe internal hosts or services unless those assets and the exact technique are explicitly in scope.

## Procedure

### 1. Establish baseline

Record the normal host, scheme, response status, canonical URL behavior, redirects, and any absolute URLs generated by the application. Identify whether a trusted reverse proxy overwrites or validates forwarded headers.

### 2. Test host-derived responses

Use a harmless controlled hostname marker on read-only endpoints. Check whether it influences absolute links, redirects, canonical tags, password-reset templates for your own account, or cacheable content. Change one header at a time.

### 3. Check proxy trust boundaries

Compare `Host` with `X-Forwarded-Host`, `Forwarded`, and `X-Forwarded-Proto` only where the deployment indicates they are relevant. Observe duplicate or conflicting header handling using a harmless request; do not use parser desynchronization or request-smuggling payloads under this skill.

### 4. Validate password-reset link generation safely

If permitted, initiate a reset only for a test account you control. Inspect the generated link in the test inbox and confirm whether the destination host is derived from untrusted input. Do not follow or disclose any real reset token. A host appearing in a response is not proof of a usable token leak.

### 5. Check cache interactions

If a host-derived response is cached, route to `attack-cache-poison`. Do not attempt to store malicious content or expose cached data to other users as a proof.

### 6. Confirm impact and cleanup

Verify that an attacker can influence a security-relevant destination or routing decision, not just an echo header. Restore test-account state and redact tokens, emails, internal addresses, and secrets.

## Common false positives

- The edge proxy normalizes the host before the application sees it.
- An absolute URL uses a configured canonical host.
- A host value is reflected but never used for routing or security-sensitive link generation.
- A reset email contains a safe fixed-domain link despite the request header.
- An internal hostname is mentioned in an error but is not reachable or exploitable.

## Evidence and output

Record `endpoint`, `header_variant`, `baseline_host`, `observed_host_use`, `proxy_behavior`, `cache_interaction`, `test_account_only`, `impact`, `cleanup_status`, and redacted evidence. Never include reset tokens or real-user addresses in reports.
